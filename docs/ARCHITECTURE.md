# Архитектура P0

## Документ и задачи

`Plan` состоит из переносимого документа (`schemaVersion`, `title`, `blocks`, `tasks`) и локальных полей (`id`, `createdAt`, `updatedAt`, `version`). Параграфы и другие блоки — данные BlockNote. Пользовательские `task`, `reference`, `callout`, `divider`, `image` зарегистрированы через `createReactBlockSpec`.

Блок задачи содержит `props.taskId`, а структурированные поля находятся в `plan.tasks[taskId]`. `TaskCard` получает сущность из React-контекста. Удалённые сущности остаются в памяти до перезагрузки редактора для undo; `toPortable` исключает задачи, на которые документ больше не ссылается. ID задачи может появляться в нескольких блоках: все они показывают одну сущность. Количество задач учитывает уникальные сущности.

BlockNote загружается через `next/dynamic` с `ssr: false`. Layout и route wrappers — Server Components; экраны с IndexedDB и событиями — Client Components. Один `PlanRenderer` и одна схема используются редактором, предпросмотром, импортом, историей и общим viewer. Read-only режим отключает BlockNote UI и заменяет поля задач/референсов на обычное содержимое.

## IndexedDB

`PlanDatabase`, имя `ipos-content-plans`, версия структуры Dexie **1**:

| Таблица   | Ключ | Индексы           | Назначение                                |
| --------- | ---- | ----------------- | ----------------------------------------- |
| plans     | id   | updatedAt         | текущие локальные документы               |
| activity  | id   | planId, createdAt | локальные события действий                |
| revisions | id   | planId, createdAt | полные резервные снимки                   |
| settings  | key  | —                 | отметка однократного добавления демоплана |

Версия IndexedDB, `schemaVersion` переносимого файла и `Plan.version` решают разные задачи: миграция таблиц, совместимость формата и контроль конкурирующих записей соответственно. Полные документы никогда не записываются в localStorage.

`usePlan` держит рабочую копию, очередь сохранений и счётчик изменений. Debounce — 700 мс. Если пользователь продолжил ввод во время записи, завершившаяся запись обновляет только локальные поля версии/времени; более свежий текст сохраняется следующим заданием. Сохранение версии, share, preview и замена вызывают `flush` и ждут очередь. Экспорт берёт текущий валидный черновик без обязательной записи: это позволяет сохранить копию после конфликта вкладок. Навигация назад тоже ждёт запись. Visibility change инициирует сохранение; beforeunload предупреждает при незавершённых изменениях. Асинхронная запись при принудительном закрытии браузера не гарантируется.

Repository проверяет `Plan.version` внутри write-транзакции IndexedDB. Вторая вкладка не может молча перезаписать изменения первой. Ошибка не выдаётся за успешное сохранение. Удаление плана каскадно удаляет его события и версии.

## Импорт и версии

Импорт проходит JSON parsing, лимит размера/вложенности, Zod validation, сводку и read-only preview. Ввод не меняет текущий план. После подтверждения `replacePlan` в одной Dexie-транзакции создаёт снимок текущей версии, заменяет документ и добавляет событие. Ошибка любой записи откатывает всё. При создании нового плана из dashboard старого документа нет, поэтому резервировать нечего.

Ручная версия — полный `Plan` в `Revision.snapshot`. До восстановления создаётся ещё одна версия, чтобы можно было вернуть состояние перед восстановлением. Восстановление сохраняет ID исходного плана, увеличивает текущую локальную версию и заменяет содержание. Событие `PLAN_RESTORED` описывает действие; оно не является снимком.

Activity собирается по изменениям названия, созданию задачи, статусу, назначению и новым референсам, а также явным import/restore/share/create. Это локальная история одного браузера, без пользователей или аудиторских гарантий. Интерфейс показывает последние 50 событий; данные сохраняются полностью.

## Share snapshot

`toPortable` → JSON → UTF-8 → native gzip → base64url → `/view#p=…`.

Viewer читает `location.hash` только в браузере, проверяет длину, распаковывает поток с лимитом выходных данных, разбирает JSON и валидирует ту же Zod-схему. Ошибочный или неподдерживаемый снимок показывает понятное сообщение. Обработка hashchange защищена от устаревших async-результатов.

Фрагмент не входит в HTTP-запрос к Next.js. Viewer не загружает или сохраняет планы в IndexedDB. Внешние URL изображений могут запрашиваться браузером; они используют no-referrer. Старый токен никогда не заменяется ссылкой на локальный ID, поэтому снимок сохраняет прежнее содержимое после изменений автора.

Ссылка не является системой доступа: содержимое видно любому обладателю. Реального server endpoint, permissions, аккаунтов, realtime или cloud storage нет. На localhost ссылка не работает на другом устройстве; для этого интерфейс должен быть доступен по общему адресу.

## Будущая миграция

Схемы, task ID, portable format и renderer не привязаны к IndexedDB. При отдельно согласованном переходе к API + PostgreSQL операции `features/plans/repository.ts` можно заменить настоящими API-запросами. Миграция потребует реального ownership, аутентификации, контроля версий, транзакций, импорта локальных данных и политики изображений. В P0 абстракции этих сервисов заранее не строятся.

Использованные первичные источники: [BlockNote custom blocks](https://www.blocknotejs.org/docs/features/custom-schemas/custom-blocks), [BlockNote shadcn](https://www.blocknotejs.org/docs/getting-started/shadcn), [shadcn Dialog](https://ui.shadcn.com/docs/components/radix/dialog), [shadcn Field](https://ui.shadcn.com/docs/components/radix/field). Next.js APIs дополнительно сверены с документацией установленного пакета `node_modules/next/dist/docs`.
