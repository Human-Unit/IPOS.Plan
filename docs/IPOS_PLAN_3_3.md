## Architecture decision and milestones

Keep IndexedDB layout/version 1. People are strictly validated `person:<UUID>` settings records with an independent edit version, aliases, role, specialization, membership, notes and timestamps. Migrate each old saved-name row once by its source key to a distinct candidate; do not delete rows, infer membership, link tasks or merge names. Candidate -> active requires a deliberate edit.

Store stable task/person associations as optional **local Plan metadata**, keyed by task ID, with selected person IDs, assignment-time display names and any explicitly preserved legacy text. Plan ID is the containing entity. This uses the existing optimistic save queue and transactional Plan/revision boundary instead of a second asynchronous assignment writer. Portable schema v1 remains text-only. Derive counts from unique live referenced tasks and valid local links; never infer identities by matching assignee text. Retain working-copy identity metadata for native undo, prune deleted tasks at persistence, and clear inconsistent links after explicit legacy-text editing or portable import. Preserve identity snapshots in revisions and whole-plan duplication; native task duplication needs explicit ID mapping.

Backups use a versioned v2 envelope with people and local associations while accepting v1 backups. Restore copies people with fresh IDs without overwriting/matching names, remaps references in current plans/revision snapshots/activity, and retains one atomic restore transaction. No portable format, table or index migration is needed.

## Using the people workflow

1. Dashboard → **Активисты** → **Добавить человека**. Only a name is required. The default is **Кандидат**; explicitly select **Активист** to confirm membership. Role, seven specializations, aliases (one per line) and local notes are optional. Search includes aliases, case folding and е/ё normalization. Membership and specialization filters combine with search.
2. Open a profile to edit details, see all current assignments and their summary, filter the task list, or review saved events. Same-name profiles remain separate; the directory and picker show short IDs and role/status to distinguish them. A concurrently changed profile cannot be overwritten by a stale open form.
3. In a task's **Свойства**, search **Выбрать людей**, tick one or more profiles and press **Применить назначение**. Ticking is only a draft selection. An existing text assignment is retained unless **Сохранить исходный текст** is explicitly unchecked. The preview shows the resulting document text before applying.
4. **Добавить нового человека** creates a separate candidate inline without leaving the brief. Creating a profile does not assign it until **Применить назначение**. **Снять привязки людей** removes confirmed links, retaining any deliberately preserved legacy text. Directly typing **Ответственные** keeps the text and clears links, because a text match cannot prove identity.
5. The task card and Assignments panel link to confirmed profiles. A profile assignment opens `/plan/<planId>#task=<taskId>`, unfolds/selects the exact first live brief, and scrolls it into view. A missing task shows an explicit alert; a missing plan/profile has a recovery link. Previous/next/current task controls and Assignments-panel jumps remain available. No global shortcut overrides BlockNote typing.
6. **Нагрузка команды** presents actual current counts for each profile, with person/status/plan/deadline filters. Deadline from/to dates are inclusive; an inverted range is explained. Expand **Задания** for the matching source tasks.
7. **Проверка текстовых назначений** lists untouched unlinked assignment strings. Whole-label alias or near-spelling suggestions are advisory links only. Open the exact brief to make an explicit link; add aliases in the profile editor. Group labels and compound strings are never automatically split or assigned.

## Persistence, consistency and history

`personSchema` validates UUIDs, names (80 characters), up to 20 unique aliases, role (120), specialization enum, membership, local notes (2000), ISO timestamps and optimistic `version`. Repositories validate at the write boundary, enforce a 1000-profile cap, and use settings transactions. There is no name uniqueness constraint. Old `activist:*` rows migrate idempotently by `sourceKey`, each into a separate candidate; original rows remain intact. Invalid old rows are reported rather than silently removed. The old splitting helpers remain only for legacy compatibility/tests; the UI no longer calls them to collect names from arbitrary task text.

Local `Plan.assignments[taskId]` contains `{legacyText, people: [{personId, name}]}`. A confirmed assignment has 1–20 distinct UUIDs and a combined text limit of 200 characters, matching `Task.assignee`. The containing plan ID plus task ID identifies the assignment. Repository saves check that every referenced person exists inside the same transaction, update the plan/activity atomically, and retain existing optimistic concurrency. Profile renaming does not rewrite saved assignment text; explicitly applying the picker uses current display names.

Whole-plan duplication preserves local people references in a new plan; duplicating a brief maps task IDs to the new task while retaining people IDs. Portable import is deliberately text-only and clears previous local associations when replacing a plan. Revisions preserve and restore local associations after validation. Native deletion excludes orphan links/counts from persisted plans while keeping the working copy available for BlockNote undo; deleting a plan removes its assignments, activity and revisions, leaving the directory intact.

Counts are derived from unique live referenced task IDs in each saved plan. Repeated blocks count once; undo-only task objects count zero. Each contributor to a shared task sees that task once. Completed/cancelled tasks are not overdue. Profile headline totals cover all its assignments; list filters do not silently change that headline. Team table counts follow the displayed filter. Date windows mean **task deadlines**, never completion dates. Counts are not hours, availability guarantees or a productivity ranking.

Person history only attributes persisted `TASK_*` events carrying `metadata.identityVersion: 1` plus `personIds`/`previousPersonIds`; original text-only events are not retroactively assigned by name. Unlink events retain previous IDs. The profile shows the latest 30 matching events. Existing plan deletion removes its history. No completion timestamp or unavailable historical contribution is invented.

## Backup v2 and portable compatibility

| Boundary | Result |
| --- | --- |
| IndexedDB schema | Existing version 1, four tables and indexes retained |
| Local plan/revision | Optional validated assignments and preserved name snapshots |
| Portable JSON v1 | Original `Task.assignee` text; no directory IDs, aliases, status or private notes |
| Share snapshot / Viewer | Same text-only portable v1; no profile lookups or local profile links |
| DOCX / print | Responsible names remain plain document text; official emblem/A4 styling retained |
| Library export | `formatVersion: 2`, schemas `{database:1, portable:1, people:1}`, root `people` array and local plan/revision associations |
| Old library input | Strict v1 accepted and normalized; saved labels become separate candidates without automatic task links |

Full backup validates duplicate IDs/keys, missing person references in current plans and revisions, versioned event references, original migration records, and plan/history relationships before writing. Identical display names are valid. Existing size/depth/node/prototype guards remain: 50 MiB library, 1 MiB portable plan, 1000 plans, 10000 revisions, 50000 events; at most 1000 people, 1000 saved legacy labels and 500 local templates. Exceeding restored directory/template/label limits aborts the whole transaction. No external image downloads occur during export/restore.

Both restore strategies **copy people with fresh UUIDs**, even when conflicting plans are skipped. The confirmation explains this behavior. `copies` remaps plan IDs; `skip` retains new nonconflicting plan IDs and excludes the history of skipped plans. Accepted current/revision assignments and versioned activity IDs are remapped to restored people. Existing people/plans/history are never overwritten or name-merged. A legacy setting key with different data gets a new key and its `sourceKey` follows it; an identical original setting can be retained as the same migration source. One transaction writes plans/revisions/activity/settings/people and the old-label migration, including rollback on quota/person-write failure.

A portable JSON file/share link is not a backup of people. To transfer profiles, aliases, notes, membership and identity links between origins, download the full library backup. It is ordinary local JSON and contains those local notes. Repeat restoration intentionally creates separate profile copies; there is no automatic cross-library identity reconciliation.
